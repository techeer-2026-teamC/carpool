# 좌석 1개에 3명이 동시에 신청하면? — 카풀 동시성 제어를 낙관적 락으로 푼 이야기

2026년 상반기, 카풀 매칭과 실시간 위치 공유 서비스를 주제로 프로젝트를 시작했다.

이 주제를 선택한 이유는 단순했다. 기술적으로 도전적인 문제를 직접 부딪혀보고 싶었기 때문이다. 토이 프로젝트에서 대규모 트래픽을 경험하기란 쉽지 않다. 하지만 실시간 위치 데이터는 다르다. 사용자가 많지 않아도 초 단위로 쏟아지는 위치 정보 자체가 고빈도 데이터 처리 경험을 자연스럽게 만들어준다. 카풀 특성상 남은 좌석에 여러 사용자가 동시에 신청하는 상황도 마찬가지다. 억지로 만들어야 하는 시나리오가 아니라, **서비스 구조 자체에서 동시성 문제가 필연적으로 따라온다.**

백엔드 개발자라면 한 번쯤 제대로 풀어봐야 할 문제들이 이 주제 안에 자연스럽게 녹아 있었다. 이 글은 그중 하나, **"남은 좌석에 대한 동시 신청"** 문제를 푼 기록이다.

---

## ① 문제 상황 — 남은 좌석 1개, 신청 버튼을 누른 3명

카풀 게시글에는 정원(`maxPassengers`)이 있다. 정원이 차면 마감된다. 그런데 인기 있는 카풀은 **마지막 한 자리**를 두고 여러 명이 거의 동시에 신청 버튼을 누른다.

상황을 구체화해보자. 정원이 3명인데 이미 2명이 탑승해서 **남은 좌석은 1개**다. 이때 A·B·C 세 명이 같은 순간 신청한다.

신청 로직은 단순하다.

```
1. 게시글을 읽는다 (currentPassengers 확인)
2. 정원이 안 찼으면 → currentPassengers + 1 해서 저장
3. 신청 성공 응답
```

아무 동시성 처리 없이 이 로직을 그대로 돌리면 어떻게 될까?

```
시각   요청 A                     요청 B                     요청 C
t1     current=2 읽음
t2                                current=2 읽음
t3                                                           current=2 읽음
t4     2 < 3 → 통과
t5                                2 < 3 → 통과
t6                                                           2 < 3 → 통과
t7     +1 → 3 저장 / "성공"
t8                                +1 → 3 저장 / "성공"        ← A를 덮어씀
t9                                                           +1 → 3 저장 / "성공"  ← 또 덮어씀
```

**세 명 모두 "신청 성공" 응답을 받는다.** 그리고 DB의 `currentPassengers`는 (덮어쓰기 때문에) 3으로 찍히거나, 구현에 따라 4·5까지 올라간다. 어느 쪽이든 **남은 좌석 1개에 3명이 확정된 상태** — 정원 3명짜리 카풀에 5명이 타게 된다.

## ② 왜 이게 문제인가 — Race Condition과 Lost Update

이건 전형적인 **레이스 컨디션(race condition)** 이다. 여러 트랜잭션이 "읽고 → 판단하고 → 쓰는" 과정을 동시에 진행하는데, 각자 **다른 트랜잭션이 끼어들기 전의 옛날 값**을 보고 판단한다.

핵심 깨짐은 두 가지다.

- **Lost Update(갱신 손실)**: A가 `2→3`으로 올려 저장한 걸, B가 자기가 읽은 옛 값(2) 기준으로 `2→3`을 저장하며 **A의 갱신을 덮어쓴다.** 분명 두 번 증가했는데 결과는 한 번만 반영된다.
- **비즈니스 불변식(invariant) 위반**: "탑승 인원 ≤ 정원" 이라는, 절대 깨지면 안 되는 규칙이 깨진다. 정원 초과 탑승은 환불·분쟁·신뢰 하락으로 직결되는 **실제 사고**다.

게다가 평소엔 멀쩡하다는 게 함정이다. 신청이 띄엄띄엄 들어오면 t1~t9가 겹치지 않아 문제가 안 보인다. **딱 "마지막 한 자리에 동시 신청"이 몰리는 순간에만** 터진다. 재현이 어렵고, 터지면 데이터가 이미 깨진 뒤다.

## ③ 해결 방법 탐색 — 네 가지 선택지

동시성으로 불변식을 지키는 방법은 여러 가지다. 각각을 카풀 신청 시나리오에 대입해 검토했다.

| 방법 | 동작 | 장점 | 단점 |
|---|---|---|---|
| **DB 유니크 제약** | `(post_id, applicant_id)` 유니크 인덱스 | 가장 단순·확실 | "정원 초과"가 아니라 "**중복 신청**"만 막음. 서로 다른 사람의 동시 신청엔 무력 |
| **비관적 락** (`SELECT ... FOR UPDATE`) | 읽을 때 행을 잠금, 끝날 때까지 남이 못 읽음 | 충돌을 아예 차단, 직관적 | 충돌이 **없을 때도** 매번 잠금 → 처리량 저하, 락 대기·데드락 위험 |
| **낙관적 락** (`@Version`) | 안 잠그고 진행, 커밋 때 버전 비교해 충돌이면 예외 | 평상시 오버헤드 0, 데드락 없음 | 충돌 시 **재시도 로직 필요**, 충돌 잦으면 재시도 비용 |
| **분산 락** (Redis `SETNX` 등) | 외부 저장소에 락 키 | 여러 인스턴스/DB 넘어선 락 가능 | 인프라 추가, 락 TTL·해제 실패 등 운영 복잡도 ↑ |

정리하면 — 유니크 제약은 **중복 신청 방지용**으로는 필수지만 정원 경쟁 자체는 못 막고(그래서 우리는 이것도 **함께** 썼다), 분산 락은 단일 DB 한 대로 충분한 지금 규모엔 과한 인프라다. 결국 후보는 **비관적 락 vs 낙관적 락**으로 좁혀졌다.

## ④ 선택 — 낙관적 락 + 재시도, 그리고 그 이유

핵심 질문은 하나였다. **"이 충돌이 얼마나 자주 일어나는가?"**

카풀 신청 충돌은 **드물다.** 대부분의 신청은 자리가 넉넉할 때 들어오고, 경쟁은 오직 "정원 임박, 막판 몇 자리" 순간에만 잠깐 몰린다. 즉 **충돌 없는 경로가 99%**다.

- **비관적 락**은 충돌이 없는 99%의 신청에도 매번 행을 잠근다. 안 일어날 사고를 대비해 늘 비용을 내는 셈이다.
- **낙관적 락**은 평상시엔 아무것도 잠그지 않다가, **충돌이 실제로 난 순간에만** 재시도 비용을 낸다.

read-heavy + 가끔 경쟁인 이 워크로드엔 낙관적 락이 맞았다.

### 구현 — `@Version`

`Post`에 버전 컬럼을 둔다.

```java
public class Post extends SoftDeletableEntity {
    @Version
    private Long version;

    public void incrementPassengers() {
        this.currentPassengers++;
        if (this.currentPassengers >= this.maxPassengers) {
            this.status = PostStatus.CLOSED;   // 정원 차면 자동 마감
        }
    }
}
```

JPA는 UPDATE 시 자동으로 `WHERE id = ? AND version = ?`를 붙이고 `version`을 +1 한다.

```sql
UPDATE posts SET current_passengers = 3, version = 6
WHERE id = 42 AND version = 5;   -- 그 사이 누가 먼저 커밋해 version이 6이 됐으면 0 rows
```

갱신된 행이 0건이면 "내가 읽은 사이 누가 바꿨다"는 뜻 → `ObjectOptimisticLockingFailureException`이 터진다. 앞의 t8·t9에서 B·C는 **A가 이미 version을 올려버려** 저장에 실패한다. Lost Update가 원천 차단된다.

조회-후-수정 경로에선 읽는 시점에 버전 검증을 강제하려고 `@Lock(LockModeType.OPTIMISTIC)`도 함께 걸었다.

```java
@Lock(LockModeType.OPTIMISTIC)
@Query("SELECT p FROM Post p WHERE p.id = :id AND p.deleted = false")
Optional<Post> findByIdAndDeletedFalseWithLock(@Param("id") Long id);
```

그리고 "같은 사람이 두 번 신청"은 `(post_id, applicant_id)` **유니크 제약**으로 별도로 막는다. 낙관적 락(정원 경쟁) + 유니크 제약(중복 신청)이 각자 다른 깨짐을 담당한다.

### 충돌하면? — 재시도가 진짜 핵심

낙관적 락은 "충돌하면 예외"로 끝이 아니다. 충돌한 B·C에게 곧장 "실패"를 주면, 사실 **자리가 아직 남았는데도** 거절한 게 될 수 있다(A만 성공, 자리는 0개로 마감됐다면 정당하지만 — 자리가 2개였다면 B도 성공해야 했다). 그래서 충돌한 요청은 **버린 게 아니라 다시 시도**해야 한다.

```java
@Retryable(
        retryFor = ObjectOptimisticLockingFailureException.class,
        maxAttempts = 5,                                   // 신청 생성: 경쟁 최다 → 5회
        backoff = @Backoff(delay = 50, multiplier = 1.5, random = true)  // 지수 + 지터
)
@Transactional
public ApplicationResponse apply(Long postId, Long applicantId) { ... }
```

재시도하면 B는 **새 트랜잭션에서 최신 상태를 다시 읽는다.** 이번엔 `current=3`을 보고 "정원 마감"으로 정상 거절되거나, 자리가 남아 있으면 성공한다. 즉 **재시도가 "옛날 값으로 잘못 판단한 것"을 "최신 값으로 다시 판단"하게** 만든다.

> ⚠️ 주의: `@Retryable`이 `@Transactional`을 **감싸야** 한다. 그래야 충돌로 롤백된 뒤 *새 트랜잭션*에서 다시 읽는다. 순서가 반대면 깨진 트랜잭션 안에서 재시도해 의미가 없다.

## 재시도 정책 — 어떤 백오프를 고를 것인가

재시도는 "그냥 다시 하면 되는" 게 아니다. **언제, 몇 번, 얼마 간격으로** 다시 할지가 정책이다. 후보를 비교했다.

| 정책 | 간격 | 문제/특징 |
|---|---|---|
| **재시도 없음** | — | 충돌 즉시 실패. 자리가 남아도 거절될 수 있어 사용자 경험 나쁨 |
| **즉시 재시도** (delay 0) | 0, 0, 0 … | 충돌한 요청들이 **동시에 또 부딪힘** → 충돌 폭증(busy loop) |
| **고정 간격** (fixed) | 50, 50, 50 … | 단순하지만 동시 충돌자들이 **같은 리듬으로 재시도** → 또 같이 부딪힘 |
| **지수 백오프** (exponential) | 50, 75, 112 … | 간격을 점점 벌려 경합 완화. 하지만 여전히 **모두 같은 시점**에 재시도 |
| **지수 + 지터** (exp + jitter) ✅ | 50±, 75±, 112± … | 간격에 무작위성 → 재시도 시점이 **흩어져** 충돌 확률 최소 |

마지막을 골랐다. `@Backoff(delay = 50, multiplier = 1.5, random = true)`가 바로 **지수 백오프 + 지터**다.

**왜 지터가 결정적인가?** 동시에 충돌한 A·B·C가 *똑같은* 간격으로 재시도하면, 다음 라운드에서도 정확히 같은 순간에 만나 또 충돌한다(thundering herd). 간격에 무작위성을 섞으면 B는 60ms 뒤, C는 80ms 뒤에 재시도하는 식으로 시점이 어긋나 서로를 비켜간다.

### 실측 — 정책을 바꿔가며 직접 돌려봤다

말로만 "지터가 좋다"고 할 게 아니라 실제로 측정했다. **하나의 게시글 row(`@Version`)에 50개 VU가 30초 내내 동시 쓰기**를 날려 낙관적 락 충돌을 강제로 만들고, 재시도 정책을 `none / immediate(0ms) / fixed(50ms) / exp(50ms×1.5) / exp+jitter` 로 바꿔가며 **재시도 횟수**와 **사용자 대기시간**을 잰다. (실험용 엔드포인트 `POST /api/v1/exp/applications/contend?policy=...` + 프로그래매틱 `RetryTemplate`, small 2vCPU/2GB, 서버 메트릭 `carpool_exp_retry_*` + k6 latency)

| 정책 | 처리량(req) | 성공률 | 요청당 재시도 | 대기 median | 대기 p95 | 대기 max |
|---|---|---|---|---|---|---|
| **none** (재시도 없음) | 19,473 | **9.4%** | 0.00 | 81ms | 191ms | 748ms |
| **immediate** (0ms) | 15,286 | 39.3% | **3.02** | 102ms | 163ms | 304ms |
| **fixed** (50ms) | 18,977 | 85.0% | 0.88 | 34ms | 242ms | 402ms |
| **exp** (50ms×1.5) | 18,442 | 91.8% | 0.49 | 35ms | 444ms | 586ms |
| **exp + jitter** ✅ | 18,154 | **93.1%** | **0.40** | 35ms | 534ms | 744ms |

![재시도 정책 스윕 결과](images/retry_policy_sweep.png)

읽어보면 재밌는 게 많다.

- **재시도가 없으면(none)**: 경합 시 **90.6%가 즉시 409**. "충돌하면 그냥 실패"는 사용자에게 너무 가혹하다 — 재시도의 존재 이유 자체.
- **즉시 재시도(immediate)는 최악**: 성공률 39%에 그치는데 **요청당 3.02회**나 재시도한다(busy-loop). 재시도 폭주가 CPU를 잡아먹어 median 대기도 102ms로 가장 느리고 처리량(req)도 최저. "백오프 없이 바로 다시"는 불 끄려고 기름 붓는 격.
- **백오프를 넣는 순간 median이 34ms로 뚝 떨어진다**(fixed/exp/jitter). 첫 시도에 성공한 다수는 빠르게 반환되고, 재시도 비용은 충돌한 소수에게만 부과되기 때문. 간격을 두는 것만으로 경합이 풀린다.
- **지터가 성공률 최고(93.1%) + 요청당 재시도 최소(0.40)**. 무작위로 재시도 시점을 흩어 thundering herd를 완화한 효과가 숫자로 확인됐다.

그런데 정직하게 짚을 반전이 하나 있다.

> ⚠️ **지터는 꼬리 지연(p95 534ms, max 744ms)이 가장 길다.** 간격을 무작위로 벌리니, 여러 번 재시도하게 된 *불운한* 요청은 더 오래 기다린다. 즉 지터는 **시스템 전체의 경합(재시도 총량·실패율)을 줄이는 대신, 개별 요청의 꼬리 지연을 양보**한다. "모든 면에서 최고"가 아니라 명확한 트레이드오프다.

우리는 **전체 성공률과 DB 경합 최소화**가 꼬리 지연보다 중요하다고 판단했다 — 신청 충돌은 가끔·짧게만 몰리고, 그 순간 일부 요청이 수백 ms 더 기다리는 건 수용 가능하다. 그래서 `exp + jitter`를 골랐다.

> 🔬 이 수치는 **한 row에 50 VU가 30초 내내** 쓰는 *극단적* 경합 스트레스다(실제 "막판 한 자리"의 짧은 경합보다 훨씬 가혹). 정책 간 **상대 비교용**이지 실트래픽 절대값이 아니다.

### 재시도 대기 시간 — 이론값 (per-attempt)

Spring의 `ExponentialRandomBackOffPolicy`는 각 간격을 `직전 간격 × U(1, 1.5)` 무작위 배수로 늘린다. 기대값 기준:

| 재시도 회차 | 기대 대기 (직전 × 1.25 평균) | 누적 |
|---|---|---|
| 1차 재시도 전 | ~50ms | 50ms |
| 2차 | ~75ms | 125ms |
| 3차 | ~112ms | 237ms |
| 4차 (maxAttempts=5의 마지막) | ~169ms | **~406ms** |

최악(5회까지 충돌)에도 사용자 체감 추가 지연은 **수백 ms 수준**이고, 지터 덕에 실제론 대부분 1~2회 안에 성공한다. *(이 표는 백오프 공식 기반 예상치이며 실측이 아니다.)*

### `maxAttempts`는 경로마다 다르게

```
ApplicationCreateService.apply  (신청 — 경쟁 최다)   → 5회
ApplicationStatusService.accept (방장의 승인)         → 3회
ReviewCreateService.createReview(리뷰 → 평점 반영)    → 3회
```

신청은 마지막 한 자리에 가장 많이 몰리니 재시도 여유를 크게(5회), 그보다 경쟁이 덜한 승인·리뷰는 3회로 뒀다. **재시도 횟수는 "충돌이 얼마나 몰리는가"에 맞춰 차등**을 줬다.

### 재시도를 다 써도 실패하면

5번을 시도해도 계속 충돌하면(=정말로 자리가 없다는 뜻) 예외를 사용자에게 정직하게 돌려준다. `GlobalExceptionHandler`가 **409 Conflict**로 변환하고, 모니터링용으로 충돌 카운터를 올린다.

```java
@ExceptionHandler(ObjectOptimisticLockingFailureException.class)
public ResponseEntity<ErrorResponse> handle(...) {
    carpoolMetrics.incrementOptimisticLockConflict();   // carpool_optimistic_lock_conflicts_total
    return ResponseEntity.status(CONFLICT).body(...);   // 409
}
```

## ⑤ 결과 — 정원은 정확히 지켜진다

부하 시나리오는 명확하다. 정원 3명인 글 하나에 **SCALE명이 동시에** 신청(`autoAccept`로 신청 즉시 탑승 → 락 경쟁 최대화)하고, 다음을 검증한다 (k6 `04_race_condition.js`).

```js
thresholds: {
  'successful_applications': ['count<=3'],     // 성공은 정원(3) 이하여야
  'checks{type:apply_result}': ['rate>0.99'],  // 201 or 409만 나와야
}
```

| SCALE (동시 신청자) | 성공(201) | 거절(409) | 핵심 |
|---|---|---|---|
| 10 | 3 | 7 | 충돌 카운터 소폭 |
| 100 | 3 | 97 | `conflicts_total` 급증 (재시도 발생) |
| 1,000 | 3 | 997 | 재시도·지터로도 **정원은 정확히 3 유지** |

**달라진 점**:

- 적용 전: 동시 신청 시 세 명 모두 성공 응답 + 정원 초과 탑승 (데이터 정합성 깨짐).
- 적용 후: **SCALE을 10 → 100 → 1,000으로 아무리 키워도 성공은 항상 정확히 3.** 동시성 안전성이 "운(타이밍)"이 아니라 "락"으로 보장된다.
- 충돌은 즉시 실패가 아니라 재시도로 흡수돼, 자리가 남아 있는 한 사용자는 성공한다. 정말 자리가 없을 때만 409.
- 충돌 급증은 Grafana `carpool_optimistic_lock_conflicts_total`로 관찰 가능 — "지금 경쟁이 몰리고 있다"가 메트릭으로 보인다.

## 정리

> 같은 좌석에 동시에 신청하는 건 카풀 서비스에서 **피할 수 없는** 구조적 동시성 문제다.
> - **문제**: 락 없이는 세 명 모두 성공 → 정원 초과(Lost Update).
> - **선택**: 충돌이 드문 워크로드라 비관적 락 대신 **낙관적 락(`@Version`)** — 평상시 비용 0, 충돌 때만 비용.
> - **재시도**: 지수 + **지터** 백오프로 thundering herd를 피하고, 충돌을 사용자 모르게 흡수. 경로별로 횟수 차등(5/3회).
> - **결과**: 동시 신청 1,000명에도 정원은 정확히 3. 데이터 정합성이 타이밍이 아니라 락으로 보장된다.

*(검증 출처: 정책별 재시도 횟수·대기시간은 k6 `09_retry_policy.js` + 실험 엔드포인트로 **실측**, per-attempt 간격 표는 백오프 공식 기반 **이론값**, 정원=3 보장은 k6 `04_race_condition.js`로 검증.)*

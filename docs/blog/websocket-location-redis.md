# 스레드를 아무리 늘려도 안 풀리는 병목이 있다 — 실시간 위치 공유를 Redis로 해결한 이야기

> 카풀 서비스의 실시간 위치 공유를 만들면서, 처음엔 "스레드가 부족한가?" 하고 STOMP 스레드 풀을 튜닝했다. 효과는 있었지만 그건 다른 문제였다. 진짜 처리량 천장은 스레드를 아무리 늘려도 — 심지어 가상 스레드를 써도 — 풀리지 않았다. 결국 답은 **병목 자체를 없애는 것**, Redis였다.

---

## 0. 한 줄 요약

- **연결(connect) 지연** 병목은 STOMP 스레드 풀 튜닝(`corePoolSize 1→200`)으로 60% 개선됐다. 이건 직렬화 지점이 "스레드"였기 때문에 통했다.
- 하지만 **메시지 처리량(throughput)** 병목은 hot path의 **DB 커넥션 풀(30개) 포화**였고, 이건 스레드를 늘려도(플랫폼 풀이든 가상 스레드든) 풀리지 않는다.
- 처리량 = 커넥션 수 ÷ DB 지연으로 고정되기 때문이다. 스레드를 늘리면 못 잡은 스레드가 큐에 줄만 더 설 뿐(`pending=370`).
- **Redis로 hot path의 DB 접근을 0으로** 만들자 처리량이 **5k → 12.5k msg/s (2.4배)**로 뛰었다. 스레드는 병목을 *우회*하려는 시도였고, Redis는 병목 *자체*를 제거했다.

---

## 1. 배경 — 운행 중 실시간 위치 공유

카풀 서비스는 운행 중 드라이버와 승객이 서로의 위치를 실시간으로 본다. 드라이버가 약 1초마다 위치를 STOMP로 보내면, 같은 운행 구독자에게 브로드캐스트하고 서버는 그 위치를 저장한다.

```
드라이버 → /app/ride/{id}/location (STOMP, ~1초마다)
         → 서버: 같은 운행 구독자에게 브로드캐스트 + 위치 저장
```

처음 구현은 단순했다. **위치를 받을 때마다 DB에 INSERT**했고, 인가(보낸 사람이 그 운행 드라이버가 맞는지)도 매 메시지 **DB SELECT(`findById`)**로 검증했다. 즉 **메시지 1건당 DB 접근 2회**.

부하테스트(k6, SCALE=1000)를 돌리기 전까지는 이게 문제가 될 줄 몰랐다.

## 2. 첫 번째 병목 — 연결 수립 지연 (그리고 스레드 풀 튜닝)

부하테스트에서 1000명이 동시에 STOMP CONNECT를 보내자 연결 지연이 폭발했다.

```
ws_connect p95 = 10,328ms   ← 비정상
```

처음엔 네트워크나 Tomcat 스레드 부족을 의심했다. 진짜 원인은 **Spring STOMP의 기본 설정**이었다.

Spring의 `ClientInboundChannel`은 기본값이 `corePoolSize=1` — **단일 스레드**다. 1000개의 CONNECT 프레임이 사실상 줄을 서서 한 번에 하나씩 처리되고 있었다.

```
ClientInboundChannel (기본값 corePoolSize=1)
  CONNECT(1) → CONNECT(2) → ... → CONNECT(1000)   ← 완전 직렬
```

> **왜 기본이 1개일까?** Spring이 의도한 설계다. 이유는 **메시지 순서 보장**. 채팅이라면 "안녕하세요"가 "반갑습니다"보다 먼저 도착해야 하니까. 하지만 **위치 데이터는 최신값만 의미가 있고 순서는 무관**하다(1초 뒤 새 값이 덮어쓴다). 그래서 순서 보장을 포기하고 병렬화할 수 있었다.

### 해결: 스레드 풀 병렬화

```java
// WebSocketConfig.java
@Override
public void configureClientInboundChannel(ChannelRegistration registration) {
    registration.taskExecutor()
        .corePoolSize(200)   // 1 → 200
        .maxPoolSize(200)
        .queueCapacity(500);
}
```

```yaml
# application-docker.yml — WS 핸드셰이크는 HTTP Upgrade라 Tomcat 스레드도 함께
server:
  tomcat:
    threads:
      max: 400   # 200 → 400
```

**결과**: `ws_connect p95` 26,247ms → 10,557ms (**60% 개선**), SCALE=100은 263ms.

여기까지는 스레드 튜닝이 정확히 통했다. **직렬화 지점이 "스레드 그 자체"였기 때문**이다. CONNECT 처리(JWT 검증 + 세션 생성)가 스레드 1개에 묶여 있었고, 스레드를 늘리니 바로 풀렸다.

### 그런데 부작용이 생겼다

플랫폼 스레드 200개는 OS 스레드와 1:1 매핑이라 각 스택이 512KB~1MB. **200개가 상시 대기하며 100~200MB를 점유**한다. t3.micro(1GB)에서 Tomcat 400 + STOMP 200을 합치면 스레드 풀만으로 수백 MB가 잠긴다.

그래서 "가상 스레드(Java 21)를 쓰면 이 메모리를 아낄 수 있지 않을까?"를 검토했다. — 그런데 여기서 더 중요한 사실을 깨달았다.

## 3. 두 번째 병목 — 스레드로는 절대 안 풀리는 천장

연결은 해결했는데, **처리량(초당 처리 메시지 수)이 ~3k msg/s에서 천장에 막혔다.** 스레드를 더 늘려도, offered rate를 올려도 처리량은 오르지 않고 오히려 출렁였다.

HikariCP 메트릭을 부하 중에 캡처해서 원인을 직접 봤다.

| 단계 | server_tps | active (max 30) | pending (대기 스레드) | 커넥션 획득 평균대기 |
|---|---|---|---|---|
| ① DB INSERT + DB 인가 | 5,020 | **30** | **370** | 119.6ms |
| ② Write-Behind + DB 인가 | 5,243 | **30** | **370** | 128.9ms |
| ③ Write-Behind + Redis 인가 | **12,528** | **1** | **0** | **0.009ms** |

①②단계의 `active=30, pending=370`이 모든 것을 말해준다.

> 인가 검증(`findById`)이 메시지 하나하나마다(초당 ~1만 건) 실행된다. 1만 건이 **커넥션 30개를 두고 경쟁**하니, 커넥션을 못 잡은 스레드 370개가 줄을 선다(`pending=370`).

여기서 핵심 인사이트가 나온다.

### 스레드를 늘리면 풀리는 병목 vs 안 풀리는 병목

**직렬화 지점이 무엇이냐**가 갈림길이다.

- **병목 A (연결)**: 직렬화 지점이 **스레드** 그 자체 → 스레드를 늘리면 풀린다. ✅ (그래서 §2가 통했다)
- **병목 B (처리량)**: 직렬화 지점이 **다운스트림 자원(DB 커넥션 30개)** → 스레드를 늘려도 안 풀린다. ❌

처리량은 대략 `커넥션 수 ÷ DB 작업 지연`으로 고정된다(Little's law). 스레드를 200개든 2000개든 늘려봐야 커넥션 30개라는 천장은 그대로고, 초과 스레드는 `pending` 큐에 줄만 더 설 뿐이다.

### 그럼 가상 스레드는?

가상 스레드를 검토했지만, **처리량 병목에는 답이 아니었다.** 두 가지 이유에서:

1. **천장은 그대로다.** 가상 스레드 수천 개를 만들어도 그들이 여전히 **DB 커넥션 30개를 두고 대기**할 뿐이다. `pending`이 싸지긴 해도(메모리), 처리량 천장은 1mm도 안 올라간다. 가상 스레드가 빛나는 건 "블로킹 I/O 대기 스레드가 많을 때 메모리를 아끼는" 상황이지, "다운스트림 자원이 천장일 때 처리량을 올리는" 상황이 아니다.

2. **위치 처리엔 CPU 작업도 섞여 있다.** STOMP 메시지 처리에는 JWT 파싱, JSON 직렬화 같은 CPU 작업이 포함된다. 가상 스레드는 블로킹 I/O 구간에서만 캐리어 스레드를 양보하므로, CPU 바운드 구간에서는 이점이 없다.

즉 가상 스레드는 **§2에서 생긴 메모리 문제(스레드 200개 점유)를 줄이는 대안**일 뿐, **§3의 처리량 천장과는 무관**했다. 스레드 레이어에서 아무리 머리를 굴려도 — 플랫폼 풀이든 가상 스레드든 — DB 커넥션이 천장인 한 처리량은 안 오른다.

**결론: 병목을 우회하지 말고, 병목을 없애야 한다.**

## 4. 진짜 해결 — Redis로 hot path의 DB 접근을 0으로

답은 명확해졌다. 매 메시지가 DB를 건드리는 구조 자체를 끊는 것.

| 단계 | 위치 저장 | 인가 검증 | 메시지당 DB 접근 |
|---|---|---|---|
| ① 베이스라인 | DB INSERT | DB SELECT(`findById`) | 2회 |
| ② Write-Behind | **Redis List push** (종료 시 일괄 flush) | DB SELECT | 1회 |
| ③ 인가 캐시 | Redis push | **Redis GET** (운행 시작 시 `rideId→driverId` 적재) | **0회** |

```java
// ① 위치마다 DB INSERT + DB 인가
Ride ride = rideRepository.findById(rideId);          // 인가 DB SELECT
rideLocationRepository.save(RideLocation.of(...));    // 위치 DB INSERT

// ② Write-Behind — 저장만 Redis로
Ride ride = rideRepository.findById(rideId);          // 인가는 아직 DB SELECT
rideLocationRedisRepository.push(rideId, lat, lng);   // 위치 Redis push

// ③ 인가도 Redis로 (운행 시작 시 cacheDriver, 종료 시 evict)
Long driverId = rideLocationRedisRepository.getCachedDriver(rideId);  // Redis GET
if (!driverId.equals(requesterId)) return;
rideLocationRedisRepository.push(rideId, lat, lng);   // DB 0회
```

### 측정으로 본 효과

| 단계 | 처리량(msg/s) | 운행 중 DB INSERT | active | pending |
|---|---|---|---|---|
| ① DB INSERT + DB 인가 | 4,792 | 매 메시지 | 30 | 370 |
| ② Write-Behind + DB 인가 | 5,226 | 0 | 30 | 370 |
| ③ Write-Behind + Redis 인가 | **11,772** | 0 | **1** | **0** |

**①→② (DB INSERT만 제거)**: 처리량 +9%에 그쳤다. 쓰기 부담은 줄었지만 **인가 SELECT가 남아 커넥션 30개 포화는 그대로**(active 30, pending 370). 여기서 "아, 쓰기를 줄여도 안 되는구나, 커넥션이 천장이구나"가 확인된다.

**②→③ (인가 SELECT 제거)**: 처리량이 **5,226 → 11,772 (2배+)**로 점프. `active 30→1, pending 370→0, 획득대기 129ms→0.009ms(약 1.4만 배↓)`. **DB 커넥션 의존이 사라지자 천장이 사라졌다.**

> 숨은 병목은 *"운행 중 안 바뀌는 값(driverId)을 매 메시지 DB로 읽는 것"*이었다. 저빈도 REST 패턴(`findById + 검증`)을 초당 1만 건의 hot path에 그대로 재사용한 비용. 운행 시작 시 Redis에 한 번 적재해두고, 메시지마다 Redis로 비교하니 끝.

### Saturation curve — 곡선으로도 드러난다

offered rate를 2k→16.7k로 올리며 지속 처리량을 측정하면:

- **①·② (커넥션 풀에 묶임)**: 전 구간 `active=30, pending≈370`. 천장이 ~3k / ~4.5k에서 막히고 출렁인다.
- **③ (커넥션 풀 미사용)**: 전 구간 `active=1, pending=0`. 천장이 **~7.9k**까지, 즉 1.7~2배 높이 올라간다.

스레드를 늘리는 접근(①②에 스레드를 더 줘봐야)으론 절대 못 넘는 선을, 병목 제거로 넘었다.

## 5. 왜 "Redis"가 최선이었나 (다른 선택지와 비교)

처리량 병목을 푸는 후보는 더 있었다. 왜 Redis였는지 정리하면:

| 접근 | 처리량 병목 해결? | 비용/한계 |
|---|---|---|
| 스레드 풀 튜닝 | ❌ (커넥션 30이 천장) | 메모리 200MB 점유 |
| 가상 스레드 | ❌ (천장 동일 + CPU 작업) | Java 21 필요, 메모리만 절감 |
| 커넥션 풀 키우기 | △ (DB 자체가 다음 천장) | 1코어 DB가 못 버팀, 근본책 아님 |
| RabbitMQ relay | ✅ (팬아웃 위임) | 인프라 추가, t3.micro 메모리 압박, 현재 규모엔 과함 |
| **Redis (Write-Behind + 인가 캐시)** | ✅ | SPOF·best-effort 유실 (수용 가능) |

Redis가 최선이었던 실무 근거:

1. **병목의 근원을 제거한다.** 다른 스레드 기반 접근은 병목을 *우회*하려 했지만, Redis는 hot path에서 DB 접근을 *없앤다*. O(1) 메모리 접근에 커넥션 풀 비의존.
2. **이미 프로젝트에 Redis가 있었다.** 알림 기능을 Redis Pub/Sub으로 이미 운영 중 → 인프라 추가 0. RabbitMQ는 컨테이너가 새로 붙고 메모리를 더 먹는다.
3. **데이터 특성과 완벽히 맞는다.** 위치 점은 best-effort(1초 뒤 새 값이 덮음)·순서 무관·최신값만 의미 → 운행 종료 시 일괄 flush하는 Write-Behind 버퍼에 천연 적합.
4. **확장 경로가 자연스럽다.** 나중에 서버를 여러 대로 늘려도, 알림과 동일하게 Redis Pub/Sub으로 멀티 인스턴스 브로드캐스트를 풀 수 있다(인메모리 브로커의 한계 해소).

### 정직한 한계

블로그에 자랑만 쓰면 신뢰가 안 간다. Redis 도입 후의 트레이드오프도 명확하다.

- **천장이 이동했다.** DB 병목은 사라졌지만 ~8k msg/s에서 다음 천장은 CPU(2 vCPU) + STOMP 인바운드/브로드캐스트로 옮겨갔다.
- **best-effort 유실.** 위치 점은 운행 종료 시 일괄 flush라, 크래시 시 진행 중 운행의 위치 점 일부가 유실될 수 있다(운행 레코드 자체는 트랜잭션으로 안전하므로 수용 가능한 트레이드오프). 내구성이 중요해지면 주기 flush + AOF로 보강.
- **SPOF.** Redis가 hot path의 단일 의존점이 됐다.

## 6. 마무리 — 배운 것

> **"스레드를 늘리면 풀리는 병목이 있고, 아무리 늘려도 안 풀리는 병목이 있다."**

직렬화 지점이 **스레드 그 자체**라면(연결 수립) 스레드 튜닝이 통한다. 하지만 직렬화 지점이 **다운스트림 자원**(DB 커넥션 30개)이라면, 스레드는 — 플랫폼 풀이든 가상 스레드든 — 그 앞에 줄만 더 세울 뿐이다. 이때 필요한 건 더 많은 스레드가 아니라 **병목 자원에 대한 의존을 끊는 것**이었다.

가상 스레드는 멋진 도구지만 "메모리를 아끼는" 도구지 "다운스트림 천장을 올리는" 도구가 아니다. 도구의 효용 범위를 정확히 아는 것 — 그게 이 작업의 가장 큰 수확이었다.

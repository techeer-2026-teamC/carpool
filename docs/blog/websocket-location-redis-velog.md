# 스레드를 200개로 늘려도 처리량이 안 올랐습니다 — 실시간 위치 공유 병목을 Redis로 잡은 이야기

> 카풀 서비스의 실시간 위치 공유를 만들면서, 처리량이 안 나와서 STOMP 스레드 풀을 1개에서 200개로 늘렸습니다. 그런데 처리량은 거의 그대로였습니다. 가상 스레드도 검토해봤지만 답이 아니었습니다. 결국 처리량을 2.4배로 끌어올린 건 스레드가 아니라 **Redis로 병목 자체를 없앤 것**이었습니다.

먼저 결론부터 말씀드리겠습니다.

- **연결(connect) 지연**은 STOMP 스레드 풀 튜닝(`corePoolSize 1→200`)으로 60% 줄었습니다. 이건 막힌 지점이 "스레드" 그 자체였기 때문에 통했습니다.
- 하지만 **메시지 처리량**이 막힌 지점은 hot path의 **DB 커넥션 풀(30개)** 이었고, 이건 스레드를 200개로 늘려도 — 심지어 가상 스레드를 써도 — 풀리지 않았습니다.
- **Redis로 hot path의 DB 접근을 0회로** 만들자 처리량이 **약 5,000 → 12,500 msg/s (2.4배)** 로 뛰었습니다.

왜 스레드가 답이 아니었고 Redis가 답이었는지, 측정값과 함께 풀어보겠습니다.

---

## 전체 여정 한눈에

세 번의 개선을 거쳤고, 각 단계가 **서로 다른 병목**을 풀었습니다.

```
[1] 스레드 풀 1→200      [2] Redis Write-Behind      [3] Redis 인가 캐시
   연결 병목 해결      →     DB 쓰기 제거         →    DB 읽기 제거 (결정타)
   ws_connect p95 60%↓      처리량 +9% (범인=DB 확인)  처리량 2.4배 ↑
```

| 단계 | 무엇을 했나 | 푼 병목 | 결과 |
|---|---|---|---|
| **1. 스레드 풀 1→200** | STOMP `corePoolSize` 200, Tomcat 400 | 연결 수립(CONNECT) 직렬화 | `ws_connect p95` 60%↓ |
| **2. Redis Write-Behind** | 위치 저장을 DB INSERT → Redis 버퍼 | 운행 중 DB 쓰기 부하 | DB 쓰기 18.6만행→0 (처리량은 +9%뿐) |
| **3. Redis 인가 캐시** | 인가 검증을 DB SELECT → Redis GET | hot path의 DB 커넥션 포화 | **처리량 2.4배 (결정타)** |

> 1번은 *연결* 병목을, 2·3번은 *처리량* 병목을 다룹니다. 그리고 **2·3번 측정은 1번(스레드 풀 200)을 고정한 상태에서** 진행했습니다 — 스레드 변수를 묶어두고 Redis 효과만 분리해 본 거죠. 이제 순서대로 보겠습니다.

## 어떤 기능이었나

카풀 서비스는 운행 중 드라이버와 승객이 서로의 위치를 실시간으로 봅니다. 드라이버가 약 1초마다 위치를 STOMP로 보내면, 서버는 같은 운행 구독자에게 브로드캐스트하고 그 위치를 저장합니다.

```
드라이버 → /app/ride/{id}/location (STOMP, ~1초마다)
         → 서버: 같은 운행 구독자에게 브로드캐스트 + 위치 저장
```

처음 구현은 단순했습니다. 위치를 받을 때마다 **DB에 INSERT**했고, 인가(보낸 사람이 그 운행의 드라이버가 맞는지)도 매 메시지 **DB SELECT(`findById`)** 로 검증했습니다. 즉 **메시지 1건당 DB 접근 2회**.

평소엔 멀쩡했습니다. 문제는 k6 부하테스트를 돌리면서 드러났습니다.

> 📌 **측정 환경 & 두 가지 테스트**: 컨테이너 small급 `2 vCPU / 2GB`, 힙 `-Xmx1024m`, HikariCP=30. 서버 실제 처리량은 `carpool_location_updates_total` 메트릭으로 측정. 스레드 풀은 전 구간 `corePoolSize=200` 고정.
> - **① 연결 부하 테스트** (1차 병목용): 1,000개 동시 STOMP 연결을 한꺼번에 수립 → `ws_connect` 지연 측정.
> - **② 처리량 포화 테스트** (2·3차 병목용): `SCALE=100`, 전송 간격 10ms(≈ offered 10,000 msg/s), 40초 → 서버 처리량 측정.

## 1차 병목 — 연결이 줄을 서서 처리되고 있었다

1000명이 동시에 STOMP CONNECT를 보내자 연결 지연이 폭발했습니다.

```
ws_connect p95 = 26,247ms   ← 정상이 아니죠 (1,000 동시 연결 테스트)
```

처음엔 네트워크나 Tomcat 스레드 부족을 의심했습니다. 하지만 진짜 원인은 **Spring STOMP의 기본 설정**이었습니다.

Spring의 `ClientInboundChannel`은 기본값이 `corePoolSize=1`, 즉 **단일 스레드**입니다. 1000개의 CONNECT 프레임이 사실상 줄을 서서 한 번에 하나씩 처리되고 있었습니다.

```
ClientInboundChannel (기본값 corePoolSize=1)
  CONNECT(1) → CONNECT(2) → ... → CONNECT(1000)   ← 완전 직렬
```

> 💡 **왜 기본이 1개일까요?** Spring이 의도한 설계입니다. 이유는 **메시지 순서 보장**입니다. 채팅이라면 "안녕하세요"가 "반갑습니다"보다 먼저 도착해야 하니까요. 하지만 **위치 데이터는 최신값만 의미가 있고 순서는 상관없습니다**(1초 뒤 새 값이 덮어씁니다). 그래서 저는 순서 보장을 포기하고 병렬화하기로 했습니다.

### 해결: 스레드 풀을 200개로

```java
// WebSocketConfig.java
@Override
public void configureClientInboundChannel(ChannelRegistration registration) {
    registration.taskExecutor()
        .corePoolSize(200)   // 1 → 200
        .maxPoolSize(200)
        .queueCapacity(500);
}
```

```yaml
# application-docker.yml — WS 핸드셰이크는 HTTP Upgrade라 Tomcat 스레드도 함께
server:
  tomcat:
    threads:
      max: 400   # 200 → 400
```

**결과**: `ws_connect p95` 26,247ms → 10,557ms (**약 60% 개선**), SCALE=100에서는 263ms.

여기까지는 스레드 튜닝이 정확히 통했습니다. **막힌 지점이 "스레드" 그 자체였기 때문**입니다. CONNECT 처리(JWT 검증 + 세션 생성)가 스레드 1개에 묶여 있었고, 스레드를 늘리니 바로 풀렸습니다.

문제는 그다음이었습니다.

## 2차 병목 — 스레드를 늘려도 처리량이 안 올랐다

연결은 해결했는데, **초당 처리하는 위치 메시지 수가 ~3,000 msg/s에서 천장에 막혔습니다.** 스레드를 더 줘도, offered rate를 올려도 처리량은 오르지 않고 오히려 출렁였습니다.

이상해서 HikariCP 메트릭을 부하 중에 직접 캡처했습니다. (아래 표는 **커넥션 풀 메트릭 캡처용 재측정 런**이라, 절대 처리량은 뒤의 "진짜 해결" 처리량 런과 런 노이즈로 조금 다릅니다 — 예: 5,020 vs 4,792. ①→②→③ 패턴은 동일합니다.)

| 단계 | server_tps | active (max 30) | pending (대기 스레드) | 커넥션 획득 평균대기 |
|---|---|---|---|---|
| ① DB INSERT + DB 인가 | 5,020 | **30** | **370** | 119.6ms |
| ② Write-Behind + DB 인가 | 5,243 | **30** | **370** | 128.9ms |
| ③ Write-Behind + Redis 인가 | **12,528** | **1** | **0** | **0.009ms** |

①②단계의 `active=30, pending=370`이 모든 걸 말해줬습니다.

> 인가 검증(`findById`)이 메시지 하나하나마다(초당 ~1만 건) 실행됩니다. 1만 건이 **커넥션 30개를 두고 경쟁**하니, 커넥션을 못 잡은 스레드 370개가 줄을 섭니다(`pending=370`).

![HikariCP active vs pending](https://quickchart.io/chart?w=640&h=360&c=%7B%22type%22%3A%20%22bar%22%2C%20%22data%22%3A%20%7B%22labels%22%3A%20%5B%22%281%29%20DB%20INSERT%22%2C%20%22%282%29%20WB%2BDB%20auth%22%2C%20%22%283%29%20Redis%20auth%22%5D%2C%20%22datasets%22%3A%20%5B%7B%22label%22%3A%20%22active%20%28in%20use%2C%20max%2030%29%22%2C%20%22data%22%3A%20%5B30%2C%2030%2C%201%5D%2C%20%22backgroundColor%22%3A%20%22%2334495e%22%7D%2C%20%7B%22label%22%3A%20%22pending%20%28threads%20waiting%29%22%2C%20%22data%22%3A%20%5B370%2C%20370%2C%200%5D%2C%20%22backgroundColor%22%3A%20%22%23e74c3c%22%7D%5D%7D%2C%20%22options%22%3A%20%7B%22title%22%3A%20%7B%22display%22%3A%20true%2C%20%22text%22%3A%20%22HikariCP%3A%20active%20vs%20pending%20per%20stage%20%28lower%20is%20better%29%22%7D%2C%20%22legend%22%3A%20%7B%22position%22%3A%20%22bottom%22%7D%7D%7D)

> ①②는 `active`가 30(최대치)에 꽉 차고 `pending`이 370까지 쌓입니다. ③(Redis 인가)에서만 `active=1, pending=0`으로 풀립니다. 커넥션을 아예 안 건드리니까요. (③의 `active=1`은 hot path가 아니라 헬스체크·종료 시 flush 같은 부수 쿼리가 잠깐 쓰는 커넥션입니다.)

여기서 제가 얻은 핵심 인사이트가 나옵니다.

### 스레드를 늘리면 풀리는 병목 vs 아무리 늘려도 안 풀리는 병목

**막힌 지점이 무엇이냐**가 갈림길이었습니다.

- **1차 병목(연결)**: 막힌 지점이 **스레드** 그 자체 → 스레드를 늘리면 풀린다 ✅
- **2차 병목(처리량)**: 막힌 지점이 **다운스트림 자원(DB 커넥션 30개)** → 스레드를 늘려도 안 풀린다 ❌

동시에 DB를 건드릴 수 있는 수가 커넥션 30개로 묶이니, 스레드를 200개든 2000개든 늘려봐야 처리량 천장은 커넥션 수에 갇힙니다. 초과 스레드는 일을 더 하는 게 아니라 `pending` 큐에 줄만 더 설 뿐입니다 — `pending=370`이 바로 그 줄입니다.

### "그럼 가상 스레드는요?"

당연히 저도 떠올렸습니다. 스레드 200개가 메모리(~100-200MB)를 상시 점유하는 게 부담스러웠으니까요. 그런데 따져보니 **가상 스레드는 처리량 병목에는 답이 아니었습니다.** 두 가지 이유에서요.

1. **천장이 그대로입니다.** 가상 스레드 수천 개를 만들어도, 그들이 여전히 **DB 커넥션 30개를 두고 대기**할 뿐입니다. 대기가 싸지긴 해도(메모리 측면) 처리량 천장은 1mm도 안 올라갑니다. 가상 스레드가 빛나는 건 "블로킹 I/O 대기 스레드가 많을 때 메모리를 아끼는" 상황이지, "다운스트림 자원이 천장일 때 처리량을 올리는" 상황이 아닙니다.
2. **위치 처리엔 CPU 작업도 섞여 있습니다.** 메시지마다 JSON 역직렬화·직렬화와 브로드캐스트 팬아웃 같은 CPU 작업이 듭니다(JWT 검증은 메시지마다가 아니라 CONNECT 1회뿐입니다). 가상 스레드는 블로킹 I/O 구간에서만 캐리어 스레드를 양보하므로, CPU 바운드 구간에선 이점이 없습니다.

즉 가상 스레드는 **1차 병목을 풀면서 생긴 메모리 부작용을 줄이는 대안**일 뿐, **2차 병목(처리량 천장)과는 무관**했습니다. 스레드 레이어에서 아무리 머리를 굴려도 — 플랫폼 풀이든 가상 스레드든 — DB 커넥션이 천장인 한 처리량은 안 오릅니다.

> ⚠️ 오해를 막기 위해 분명히 해두면, 가상 스레드는 **직접 적용해서 측정한 게 아니라 검토 단계에서 기각**했습니다. 이유는 두 가지 — ① 현재 프로젝트가 Java 17이라 적용하려면 Java 21 업그레이드가 선행돼야 하고, ② 위에서 본 것처럼 처리량 병목(DB 커넥션)과는 무관하기 때문입니다. "해봤더니 안 됐다"가 아니라 "분석으로 채택하지 않았다"가 정확합니다.

**결론: 병목을 우회하지 말고, 병목을 없애야 했습니다.**

## 진짜 해결 — Redis로 hot path의 DB 접근을 0으로

답은 명확해졌습니다. 매 메시지가 DB를 건드리는 구조 자체를 끊는 것. 두 단계로 나눠 적용했습니다.

| 단계 | 위치 저장 | 인가 검증 | 메시지당 DB 접근 |
|---|---|---|---|
| ① 베이스라인 | DB INSERT | DB SELECT(`findById`) | 2회 |
| ② Write-Behind | **Redis List push** (종료 시 일괄 flush) | DB SELECT | 1회 |
| ③ 인가 캐시 | Redis push | **Redis GET** (운행 시작 시 `rideId→driverId` 적재) | **0회** |

```java
// ① 위치마다 DB INSERT + DB 인가
Ride ride = rideRepository.findById(rideId);          // 인가 DB SELECT
rideLocationRepository.save(RideLocation.of(...));    // 위치 DB INSERT

// ② Write-Behind — 저장만 Redis로
Ride ride = rideRepository.findById(rideId);          // 인가는 아직 DB SELECT
rideLocationRedisRepository.push(rideId, lat, lng);   // 위치 Redis push

// ③ 인가도 Redis로 (운행 시작 시 cacheDriver, 종료 시 evict)
Long driverId = rideLocationRedisRepository.getCachedDriver(rideId);  // Redis GET
if (!driverId.equals(requesterId)) return;
rideLocationRedisRepository.push(rideId, lat, lng);   // DB 0회
```

### 측정 — 어디서 처리량이 뛰었나

> 아래는 **처리량 측정 런**입니다(앞 HikariCP 표와는 별도 실행이라 절대값이 조금 다름 — 4,792 vs 5,020). 측정값이 offered(~10k)보다 약간 큰 건 순간 피크 윈도우 기준이기 때문입니다.

| 단계 | 처리량(msg/s) | 운행 중 DB INSERT | active | pending |
|---|---|---|---|---|
| ① DB INSERT + DB 인가 | 4,792 | 매 메시지 | 30 | 370 |
| ② Write-Behind + DB 인가 | 5,226 | 0 | 30 | 370 |
| ③ Write-Behind + Redis 인가 | **11,772** | 0 | **1** | **0** |

**①→② (DB INSERT만 제거)**: 처리량이 +9%에 그쳤습니다. 쓰기 부담은 줄었지만 **인가 SELECT가 남아 커넥션 30개 포화는 그대로**(active 30, pending 370)였습니다. 여기서 "아, 쓰기를 줄여도 안 되네, 커넥션이 천장이구나"가 확인됐습니다.

![DB write load](https://quickchart.io/chart?w=640&h=360&c=%7B%22type%22%3A%20%22bar%22%2C%20%22data%22%3A%20%7B%22labels%22%3A%20%5B%22%281%29%20DB%20INSERT%22%2C%20%22%282%29%20WB%2BDB%20auth%22%2C%20%22%283%29%20Redis%20auth%22%5D%2C%20%22datasets%22%3A%20%5B%7B%22label%22%3A%20%22DB%20rows%20written%20%2F%2040s%22%2C%20%22data%22%3A%20%5B186402%2C%200%2C%200%5D%2C%20%22backgroundColor%22%3A%20%5B%22%23e74c3c%22%2C%20%22%232ecc71%22%2C%20%22%232ecc71%22%5D%7D%5D%7D%2C%20%22options%22%3A%20%7B%22title%22%3A%20%7B%22display%22%3A%20true%2C%20%22text%22%3A%20%22DB%20write%20load%3A%20rows%20inserted%20in%2040s%20%28lower%20is%20better%29%22%7D%2C%20%22legend%22%3A%20%7B%22display%22%3A%20false%7D%7D%7D)

> Write-Behind로 40초에 18.6만 행 쓰던 걸 0으로 만들었습니다. 그런데도 처리량은 안 올랐죠 — 쓰기가 아니라 읽기(인가 SELECT)가 커넥션을 잡고 있었으니까요.

**②→③ (인가 SELECT 제거)**: 처리량이 **5,226 → 11,772 (약 2.3배)** 로 점프했습니다(①→③로 보면 약 2.4배). `active 30→1, pending 370→0, 획득대기 128.9ms→0.009ms(약 1.4만 배↓)`. **DB 커넥션 의존이 사라지자 천장이 사라진 겁니다.**

> 숨은 병목은 *"운행 중 안 바뀌는 값(driverId)을 매 메시지 DB로 읽는 것"* 이었습니다. 저빈도 REST 패턴(`findById + 검증`)을 초당 1만 건의 hot path에 그대로 재사용한 비용이었죠. 운행 시작 시 Redis에 한 번 적재해두고 메시지마다 Redis로 비교하니 끝이었습니다.

## 왜 RabbitMQ가 아니라 Redis였나

처리량 병목을 푸는 후보는 더 있었습니다. 제가 Redis를 고른 이유를 정리하면 이렇습니다.

| 접근 | 처리량 병목 해결? | 비용/한계 |
|---|---|---|
| 스레드 풀 튜닝 | ❌ (커넥션 30이 천장) | 메모리 ~100-200MB 점유 |
| 가상 스레드 | ❌ (천장 동일 + CPU 작업) | Java 21 필요, 메모리·운영만 단순화 |
| 커넥션 풀 키우기 | △ (DB가 다음 천장으로 추정) | 1코어 DB라 미측정·근본책 아님 |
| RabbitMQ relay | ✅ (팬아웃 위임) | 인프라 추가, 메모리 압박, 현재 규모엔 과함 |
| **Redis (Write-Behind + 인가 캐시)** | ✅ | SPOF·best-effort 유실 (수용 가능) |

1. **병목의 근원을 없앱니다.** 다른 스레드 기반 접근은 병목을 *우회*하려 했지만, Redis는 hot path에서 DB 접근을 *제거*합니다. O(1) 메모리 접근에 커넥션 풀을 안 씁니다.
2. **이미 프로젝트의 핵심 인프라가 Redis였습니다.** JWT 검증 캐시 · 게시글 캐싱 · 실시간 알림(Pub/Sub)을 이미 Redis로 운영 중이었습니다. 위치 공유도 Redis로 풀면 **인프라 추가가 0**이고 운영 스택이 그대로 단순해집니다. 반면 RabbitMQ는 컨테이너가 새로 붙고 메모리를 더 먹는 데다, 익숙한 Redis를 두고 새 미들웨어를 학습·운영할 이유가 약했습니다.
3. **데이터 특성과 잘 맞습니다.** 위치 점은 best-effort(1초 뒤 새 값이 덮음)·순서 무관·최신값만 의미 → 운행 종료 시 일괄 flush하는 Write-Behind 버퍼에 딱 맞습니다.
4. **확장 경로가 자연스럽습니다.** 나중에 서버를 여러 대로 늘려도 알림과 똑같이 Redis Pub/Sub으로 멀티 인스턴스 브로드캐스트를 풀 수 있습니다.

### 솔직한 한계

자랑만 쓰면 신뢰가 안 가니, 트레이드오프도 적어둡니다.

- **천장이 이동했습니다.** DB 병목은 사라졌지만 ~8k msg/s에서 처리량이 꺾입니다. 남은 천장은 CPU(2 vCPU) + STOMP 브로드캐스트 팬아웃으로 보이며, 여기부턴 스케일아웃의 영역입니다.
- **커넥션 증설은 측정하지 않았습니다.** "커넥션 풀을 30→100으로 늘리면?"은 직접 재보지 않았습니다. 1코어 DB라 커넥션을 늘려도 DB CPU가 다음 천장일 것으로 보고, 풀을 키우기보다 hot path에서 DB 자체를 빼는 쪽을 택했습니다(이 부분은 추정입니다).
- **best-effort 유실.** 위치 점은 운행 종료 시 일괄 flush라, 크래시 시 마지막 flush~크래시 사이(1초 간격이면 그 운행이 진행된 시간만큼)의 위치 점이 유실될 수 있습니다. 운행 레코드 자체는 트랜잭션으로 안전하므로 수용 가능한 트레이드오프로 봤고, 내구성이 중요해지면 주기 flush + Redis AOF로 보강할 계획입니다.
- **SPOF.** Redis가 hot path의 단일 의존점이 됐습니다.

## 보너스 — 자주 받은 질문 (FAQ)

> 본문 결론은 위에서 끝났습니다. 아래는 스레드 풀·가상 스레드 관련 심화 Q&A라, 결론만 필요하면 마무리로 건너뛰셔도 됩니다.

**Q. 스레드 풀 1개 vs 200개, Redis가 있는 지금도 의미 있나?** — 네. 이 스레드 풀은 연결(CONNECT)과 위치 메시지(SEND)를 모두 처리해서, 1개면 둘 다 직렬화돼 막힙니다. 그리고 Redis와 상호 보완입니다 — Redis 도입 *전*엔 스레드 200개를 줘도 30개만 일하고 170개는 커넥션을 못 잡아 놀았지만, 커넥션 천장이 사라진 *후*엔 200개가 비로소 전부 일합니다. (스레드 풀 = 동시성 공급, Redis = 그 동시성을 막던 천장 제거.)

**Q. 스레드 풀 증가와 가상 스레드는 무슨 관계?** — "동시에 몇 개를 처리하느냐"를 푸는 *같은 문제의 두 해법*이라, 합치는 게 아니라 둘 중 하나를 고르는 관계입니다. "200개 플랫폼 ≈ 가상 스레드, 처리량 같고 메모리 적다"는 맞습니다 — 천장이 CPU(2 vCPU)라 둘 다 같은 ~8k에 도달하고, 차이는 플랫폼 200개가 유휴에도 스택(개당 ~512KB~1MB)을 예약하는 메모리뿐입니다.

### Q. 그럼 지금 가상 스레드를 넣으면 뭐가 해결되나?

전제로 **Java 21 업그레이드**가 필요합니다(현재 Java 17). 적용하면:

**해결되는 것**
- **상시 점유 메모리** — 플랫폼 스레드 200개 + Tomcat 400개가 유휴 상태에도 잡아먹는 ~100-200MB를 제거. t3.micro(1GB)에서 의미 있음.
- **풀 사이즈 튜닝 불필요** — `corePoolSize` 매직 넘버 고민이 사라지고, 동시 연결 폭주를 수치 설정 없이 흡수.
- **향후 대비** — 위치 처리에 외부 API 호출(ETA 재계산 등) 같은 블로킹 I/O가 추가되면, 적은 캐리어 스레드로 대량 동시 대기를 처리.

**해결 안 되는 것**
- **처리량 천장(~8k)** — 지금 천장은 CPU(2 vCPU) + STOMP 브로드캐스트라 CPU 바운드. 가상 스레드는 무력.
- **수평 확장** — 인메모리 브로커 문제는 Redis Pub/Sub / RabbitMQ relay의 몫이지 가상 스레드와 무관.

> 결론: 지금 가상 스레드의 가치는 **"성능"이 아니라 "메모리 + 운영 단순화"**입니다. 그래서 이번엔 채택하지 않고, Java 21 업그레이드 시점의 과제로 남겨뒀습니다.

## 마무리 — 배운 것

> **"스레드를 늘리면 풀리는 병목이 있고, 아무리 늘려도 안 풀리는 병목이 있다."**

막힌 지점이 **스레드 그 자체**라면(연결 수립) 스레드 튜닝이 통합니다. 하지만 막힌 지점이 **다운스트림 자원**(DB 커넥션 30개)이라면, 스레드는 — 플랫폼 풀이든 가상 스레드든 — 그 앞에 줄만 더 세울 뿐입니다. 이때 필요한 건 더 많은 스레드가 아니라 **병목 자원에 대한 의존을 끊는 것**이었습니다.

가상 스레드는 멋진 도구지만 "메모리를 아끼는" 도구지 "다운스트림 천장을 올리는" 도구가 아닙니다. 도구의 효용 범위를 정확히 아는 것 — 그게 이 작업에서 제가 얻은 가장 큰 수확이었습니다.
